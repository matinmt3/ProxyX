# ProxyX 7.1.0 WEB Proxy QA

## Scope and Evidence

This run adds Telegram WEB proxy support without replacing the existing MTProto
list. More than 200 tests means 304 distinct JVM/Robolectric test cases, not 304
manual button presses. Emulator workflows are recorded separately in the
chronological device CSV. Passing this suite does not prove that every possible
bug, public provider, Android device or network has been tested.

- Automated suite: 304 cases in 57 suites, zero failures, errors or skipped cases.
- Coverage includes Room queries/migrations, benchmark progression, sorting,
  transfer integrity and cleanup, saved-message formatting/verification,
  schedules, source parsing/quality, update validation, WEB links, frame security,
  bounded DNS, local-network failures and current-network WEB ranking.
- Six additional JavaScript runtime assertions passed in Node VM with a mocked
  DOM/native bridge: unchanged small frame, fragmentation and byte preservation,
  maximum valid frame, oversized frame rejection, invalid type rejection and
  unchanged control text. These are not Android WebView execution tests and are
  not added to the 304-case total.
- Final accessibility build and device retest: pending final verification below.

## Device Setup

- Existing ProxyX_Test emulator, Android API 34, x86_64, 720 x 1280 at 320 dpi,
  1536 MiB RAM, two cores, software rendering. The laptop has 8 GiB RAM; Gradle
  and the emulator were run separately.
- The old Google WebView 113 correctly failed the required-feature gate. For
  actual relay QA, an official AOSP WebView 128.0.6613.88 prebuilt was installed
  and selected. Its Git blob and APK SHA-256 were verified against the official
  AOSP download. This is a test component, not a recommendation to install that
  old version on production phones; use an up-to-date official WebView there.
- APK upgrades used adb install -r and the existing release certificate. No app
  uninstall, data clear, account logout, TDLib database export or session-key
  inspection was performed. Telegram authorization and original favorites were
  retained.
- Google Play services remain disabled on this AVD. No system security policy
  was bypassed and no compatible Android Telegram WEB client was installed.

## Real WEB Transfer

The public max-speed.co.uk relay completed DNS/public-address checks, an
authenticated WEB session and three genuine Telegram MTProto responses for
DC 2, 4 and 2. A protocol-only test displayed no invented download/upload speed.

After the frame interoperability fix, the opt-in TDLib file test completed all
four stages. The persisted result was TRANSFER_VERIFIED, stage 4, three completed
rounds, median protocol latency 206 ms, download 1383 KiB/s and upload 59 KiB/s.
One-way file payload was 4,718,592 bytes; both directions total 9,437,184 bytes,
excluding protocol overhead. Each round used fresh random data, removed the
local upload cache, downloaded the file and checked exact length and SHA-256.
Network identity matched the captured active network.

These are observations on that connection, not guarantees of future speed or
operator reachability. In particular, this relay had much weaker upload than
download. Balanced WEB ranking uses both directions rather than declaring it
best from its latency alone. The current-PID log had no app fatal exception,
carrier-failure warning or ignored/outside-head CSP warning during this test.

## Issues Found and Fixed

1. Offline WEB tests originally stored a generic provider failure. They now
   report local-network INCONCLUSIVE/NO_NETWORK, stage zero and zero rates.
   A real offline retest passed and radio settings were restored.
2. A document-start CSP meta element could be inserted outside the head and
   ignored. The code creates a head when absent and installs the policy there.
   A fresh real WebView relay reached stage four without the old console warning.
   Absence of that warning is not proof against every hostile provider page.
3. A public provider's bridge forwarded DATA frames up to 1 MiB, exceeding the
   native 64 KiB IPC validator. Document-start code now fragments validated DATA
   before IPC, preserving encrypted bytes, stream ID and payload order. Invalid
   oversized/control data fails closed. The preceding actual file test timed
   out with zero rates; the subsequent test completed three real file rounds.
4. Large-font landscape trust text clipped the provider/data-usage warning.
   Its body is now scrollable. On font 1.3 in landscape, a live device retest
   scrolled to the complete data-use notice while Cancel/Continue remained visible.
5. WEB controls and status are in the scrolling list, while active cancellation
   stays pinned. New imports return to the start. Stale/failed latency does not
   reorder unverified entries. Source DNS and cancellation are bounded.
6. Equal-width Vault tabs clipped English labels at font 1.3 in portrait.
   An intrinsic-width scrollable tab row preserves the full labels. Live
   selection of all four tabs and English/Persian large-font screenshots passed.
7. Mixed Persian round labels and Latin transfer units reordered numeric evidence
   in the RTL screenshot even though persisted measurements were correct.
   Numeric hostname/latency/rate runs now use explicit LTR; verified round count
   is a separate localized line. Final screenshot verification is recorded below.

Earlier FAIL rows remain in the chronological CSV. They are not erased or
silently relabeled; passing post-fix checks appear later.

## Limits

- Compatible external Telegram WEB handoff cannot be verified on this AVD;
  no activity resolves tg://webproxy. The app handles the missing client without
  crashing. It does not promise support in every Telegram version.
- Public source feeds were unreachable during parts of this run. Seven public
  starter entries were labeled untested, not fabricated healthy results. A failed
  fetch preserves existing entries; a successful public refresh replaces public
  rows and clears their old metrics while preserving manual imports.
- No physical phone, Iranian cellular operator, other ABI/API runtime, full
  1800-route completion, long sustained large-file throughput or final hardware
  Macrobenchmark/Baseline Profile run was available.
- Signed-out login/OTP and destructive logout/deletion were not repeated on the
  user's account. Long background schedules were not all waited out.
- Tests use real active-device networking for live measurements. Automated test
  fixtures never supply simulated speeds to the shipping app.
